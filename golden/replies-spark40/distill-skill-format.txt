# Skill 草稿

## 名称

`long-run-exit-based-success`

## 适用场景

当一个命令运行时间长、涉及异步任务、网络依赖不稳定，或可能产生大量输出时，用 stdout 判断成功不可靠，必须通过写盘文件来确认执行结果。

## 核心原则

**不依赖 stdout 或 exit code 作为成功的唯一判据。必须让命令把成功状态写入一个明确的文件，通过该文件判断。**

## 触发条件

- 命令执行时间 > 30 秒
- 命令涉及远程调用（数据库、API、消息队列等）
- 命令会产生大量输出，stdout 可能被截断或缓冲
- 命令的 exit code 语义不可靠（例如被管道或子进程干扰）

## 实施步骤

1. **约定输出文件路径** — 和命令的编写方约定一个固定路径，如 `/tmp/job-{name}.done` 或 `./output/{name}.success`。
2. **命令内部落盘** — 命令在确认任务完全完成（包括所有依赖都落地）后，才创建/写入该文件。文件内容可包含时间戳、版本号等元信息。
3. **调用方轮询文件** — 调用方不直接等命令结束，而是轮询目标文件是否出现，或使用 `inotifywait`、`fs.watch` 等方式监听。
4. **超时与失败处理** — 设定最大等待时间；文件未出现则视为失败，并清理残留的临时文件。
5. **清理策略** — 任务完成后可选清理文件，或根据文件做归档；如果是长期运行的服务，文件可作为上次运行成功的记录保留。

## 反模式（不要这样）

- ❌ `cmd && echo "done"` — stdout 只是 echo 回来的，不代表业务结果。
- ❌ `cmd; echo $?` — exit code 在复杂管道中经常产生误导。
- ❌ 依赖命令本身的日志输出做判断 —日志是给人看的，不是给程序用的。
