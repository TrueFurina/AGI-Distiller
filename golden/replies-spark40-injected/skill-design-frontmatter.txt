# 代码审查 Skill

## 用途
在完成一轮编码改动后，对本次改动做一次结构化审查，聚焦：功能正确、无破坏、可维护、无安全风险。不是替代 CI，而是给改动加一道"人在回路"的质量闸。

## 审查粒度
按优先级分级，只列有证据的问题，没证据不写：

- **P0** — 会导致线上错误、数据损坏或安全风险。必须修，不通过不能合。
- **P1** — 影响功能、测试或可维护性的明显问题。建议本次修掉。
- **P2** — 可选优化，可单独排期。只提不拦。

每条问题必须包含：文件位置、原因、影响、建议动作。不要写"建议优化一下某函数"这种没有信息的废话。

## 审查流程

### 第一步：拿到真实改动范围
- 不要凭记忆猜改了什么。先用 `git diff --stat` 或 `git status` 看真实变更。
- 如果改动范围大，先出改动清单，确认评审对象，避免漏审或误审。

### 第二步：从 P0 开始逐级过
按风险从高到低审，不要把时间浪费在 P2 上而漏了 P0。

**P0 必查项：**
- 数据库字段增删 / DDL 是否会影响既有数据。
- 支付、鉴权、密钥、凭据处理是否有硬编码或日志泄露风险。
- 权限校验是否被绕过（新增接口有没有鉴权）。
- SEO 模板 / 对外可见的字符串 / 路由是否被不当地改动。
- 边界条件：空值、并发、超时、资源回收。

**P1 常查项：**
- 新功能是否破坏了相邻旧逻辑。
- 异常处理是否吞掉了错误（空 catch / 只 log 不处理）。
- 测试是否覆盖了改动路径。
- 是否存在明显的坏味道（大函数、重复逻辑、魔法数字）。
