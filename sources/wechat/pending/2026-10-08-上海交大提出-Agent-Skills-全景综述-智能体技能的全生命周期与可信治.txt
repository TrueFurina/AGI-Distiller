INSIGHT · 核心洞察

“
Agent Skill 的关键价值，是把一次性上下文里的任务诀窍抽离成可检索、可执行、可维护、可治理的能力工件；当技能库开始增长，真正困难的也从“写出一个技能”转向库级维护、双目标评测与供应链信任。

今天的 LLM Agent 已经能调用工具、操作软件、编写代码并协调多个子智能体，但完成具体任务所需的 know-how 往往仍散落在提示词、代码与单次轨迹里。它能在这一次运行中起作用，却很难被命名、检索、复用和更新。

这篇综述把 Agent Skill 视为一层独立的能力基础设施：它同时描述 能做什么、怎样做、何时适用，并沿表示、构建、运行、演化、评测和治理的完整生命周期，梳理一个技能从产生到规模化使用会遇到的关键问题。

📌 一句话总结　本文系统梳理 Agent Skills，将技能定义为同时包含能力、过程与边界的可复用工件，串联表示、构建、运行、演化、评测与治理，并指出规模化可靠性仍是核心缺口。

01
DEFINITION
定义：把任务诀窍变成可复用能力工件

论文从一个很具体的缺口出发：Prompt 负责约束当前上下文，Tool 提供外部动作，Memory 保存过去经验，Workflow 固化流程，Protocol 连接组件，Subagent 承担委派执行；但 针对一类任务的操作诀窍 仍常常依附于某次运行，缺少一个能够单独存储和调用的单位。

— Figure 1｜Agent Skills 的生命周期与全文结构总览。
总览图的阅读顺序从左下角开始：先用能力、过程和边界定义技能，再进入表示与构建；中间的运行时把技能接入任务，运行结果回流到演化；右侧则把评测、安全治理和开放挑战放在库级尺度上。它传达的核心不是一个线性流水线，而是 技能工件、运行反馈与生态治理之间的闭环。

1.1为什么 Agent Skills 在 2026 年快速成为独立议题

早期 ReAct、Toolformer、AutoGen、Voyager 与 ExpeL 提供了推理行动、工具使用、多智能体和经验复用等基础。随后研究焦点开始细分：技能构建、运行时、演化、评测与安全治理分别出现专门工作，技能也从研究原型进入带有共享规范和公共仓库的平台生态。

— Figure 2｜从前置基础到 2026 年中，Agent Skill 研究覆盖的生命周期阶段持续扩展。
横轴按时间推进，彩色标签分别对应表示、构建、运行、演化、评测和安全治理；底部的活动强度箭头显示论文所观察到的月度活跃度上升。值得注意的是，2026 年春季以后不再只有“如何造技能”，还出现 SkillPager、SkillRet、SRA、SkillSieve、SkillProbe 等专门处理加载、检索、评测和安全的问题，这说明研究对象已从单个技巧扩展到 可运营的技能系统。

— Table 1｜本文与同期 Agent Skill 综述在生命周期覆盖深度上的比较。
表中每一列是一类议题，✓ 表示专门且较完整的讨论，半勾表示部分或间接覆盖。作者将自己的差异点定位在评测：同期多篇综述对表示、构建与安全已有较广覆盖，但 把技能质量与智能体用技能能力拆成两个评测目标 的处理仍不充分。这个自我定位也解释了全文后半部分为何给评测和治理较大篇幅。

1.2一个技能必须同时回答三个问题

论文把技能写成三元组 s = ⟨C，P，B⟩。C 是 Capability，说明它覆盖哪类任务；P 是 Procedure，说明执行步骤、工具调用与资源；B 是 Boundary，说明适用条件、前置依赖、权限以及失败后的退出规则。只描述“能做什么”还不够，技能还必须让智能体知道怎样落地以及何时不该使用。

— Figure 3｜本文按六个主题组织 Agent Skill 方法谱系。
这张分类图纵向列出表示、构建、运行、演化、评测和安全治理，右侧再为每个主题挂接代表方法。它的作用不是给方法排座次，而是说明同一个技能系统必须同时处理文件形态、来源、选择与执行、版本更新、效果归因以及风险控制；任何一层缺失，都会在规模化时成为瓶颈。

— Table 2｜Skill 与 Prompt、Memory、Workflow、Tool、Protocol、Subagent 的关系。
Table 2 给出最清楚的边界：Skill 并不替代这些组件。相对 Prompt，它把指导移出当前上下文以供复用；相对 Memory，它把记录过的经验转成可运行过程；相对 Workflow，它补上条件、依赖与检查；相对 Tool，它决定何时、怎样调用一个或多个工具；相对 Protocol 和 Subagent，它是被传输或被加载的 能力本身。明确这个边界后，下一步才是选择技能应以何种形式存在。

02
REPRESENTATION
表示：自然语言、可执行与混合资源

定义解决“什么是技能”，表示形式决定它能否被检索、静态检查、跨框架迁移和稳定执行。论文把现有技能分成三类，并把结构化中间表示看作一条连接可读性与可验证性的编译路径。

— Figure 4｜三种技能表示及其示例形态与权衡。
左侧的自然语言技能通常是一份 Markdown，写清适用场景、步骤与输出，最便于人类编写和修改，但歧义与隐含假设较多。中间的可执行技能直接编码成函数、脚本或工具调用，可重复、可测试，却引入依赖、权限和运行环境。右侧的混合资源技能把说明、代码、配置、模板和样例装进同一目录，表达最完整，维护成本也最高。图底部进一步指出，编译成 typed graph 或 portable IR 后，可以获得 可检查、可移植、可修复 的结构。

— Table 3｜不同表示形态的代表系统、载体与关键特征。
代表系统把差异落到具体载体上：OpenHands Microagents 与 SOP-Agent 采用文档；Voyager、LATM、PolySkill 使用代码库、可复用函数或程序化技能；Claude Code 与 Skilldex 使用带资源的技能包；Skill Text to Structure、SkCC 和 AIP 则尝试 typed graph、portable IR 与图表示。这里没有绝对最优解：越接近自然语言越灵活，越接近结构化执行越容易验证，复杂任务通常需要两者组合。

表示形式一旦确定，技能的来源就成为下一个问题：是由人和文档提供，还是从智能体自身经历中抽取，抑或在任务缺口出现时即时生成。

03
CONSTRUCTION
构建：技能从哪里来

手工编写能保证控制力，却无法覆盖不断增长的任务空间。论文因此不按具体算法，而按 知识来源 组织构建方法，因为来源直接决定技能的覆盖范围、验证成本和环境迁移风险。

— Figure 5｜三类技能来源：预先材料、历史轨迹与当前任务需求。
图中第一条路线使用运行前已经存在的 SOP、规范、API 文档或知识库，可由开发者直接写，也可经文档抽取管线生成。第二条路线从成功、失败、示范与反馈轨迹中蒸馏技能，证据可是一条成功轨迹、一组成败对照或一批轨迹。第三条路线在当前任务缺少能力时现场识别缺口、写出技能并立即运行。三者分别强调 稳定性、适应性与覆盖缺口。

3.1三种来源各自解决什么问题

预先材料适合把经过确认的人类知识转成可执行资产，例如 Claude Code 的固定目录结构、CUA-Skill 的界面操作知识和 SkillFoundry 的多源科学资源管线。历史轨迹更贴近智能体真实遇到的问题：Voyager 保留通过环境测试的行为，ExpeL 与 SWE-Exp 从成功—失败差异提炼经验，Trace2Skill 与 AWM 从轨迹池中寻找可复用模式。按需构建则由 CREATOR 或 LATM 在任务现场补齐缺失工具。

— Table 4｜技能构建方法按知识来源、应用场景与特征分组。
表格应按“Skill Source”列阅读：预先材料组包含 direct authoring 与 domain resources；历史轨迹组从 single success trace 扩展到 success–failure pair、trace pool 和 active exploration；当前任务组则只在需要时创建。论文给出的综合判断很务实：材料型技能会随文档老化，轨迹型技能可能过拟合旧环境，按需技能往往缺少验证且不被保存，因此可靠系统更可能采用 三路并存的组合策略。

构建只产生了技能工件，并不保证它在任务中被正确使用。技能进入大规模库以后，检索、激活、加载和组合会成为新的误差来源。

04
RUNTIME
运行时：从找到技能到组合执行

运行时回答的是“技能已经存在，Agent 怎样把它变成环境中的有效动作”。论文把这一过程拆成四步，且强调结果和用户反馈必须重新进入技能库。

— Figure 6｜检索、激活、加载执行与组合构成的技能运行时流水线。
先由任务与上下文形成 Query，检索只返回少量候选技能；激活阶段再根据触发器、模型判断或学习到的 selector 做出承诺；随后加载必要内容，绑定参数、依赖和权限，并在工具与环境中执行；若单个技能不足，则按序列、层级、图或回退链组合。左侧反馈箭头提醒我们，运行时不是只读消费技能库，实际结果会改变后续排序与演化。

4.1检索相关，不等于应该调用

检索信号可来自任务描述、当前状态、技能依赖或历史成功率。它解决的是候选缩小问题，却不自动解决是否应该调用。激活还需要 declared trigger、model-selected activation 或 learned selector。论文特别区分这两步，是因为语义上最相关的技能未必对当前状态有用，而一个错误激活会把后续加载与执行全部带偏。

4.2加载预算和组合结构决定执行成本

Claude Code 只常驻短元数据，触发后再加载完整说明；SkillPager 细化到只载入与查询相关的节点；SKIM 用 soft token 压缩；From History to State 与 Skill-to-LoRA 则把过程移入任务模块或适配器。组合方面，Sequence 传递前一步输出，Hierarchy 由父技能调用子技能，Graph 处理偏序依赖，Fallback 在失败后切换方案，Collaboration 把能力分配给不同 Agent。

— Table 5｜四个运行阶段的代表机制与系统。
表中可看到同一个系统可能跨阶段出现：SkillRL 用历史反馈重排技能，Claude Code 同时涉及声明式触发与按需加载，SkillX 既检索又做层级组合。由此可见，运行时的优化目标不是单点召回率，而是 从候选发现到环境效果的整条链路。链路开始长期运行后，技能本身也会因工具漂移、失败案例和新需求而需要更新。

05
EVOLUTION
演化：改技能、训策略，还是维护技能库

技能的第一版通常覆盖不全，环境和工具还会持续变化。论文按“每次更新到底改了什么”划分演化方法：直接改技能文本、用奖励联合训练策略与技能库、搜索多个候选版本，或把技能行为蒸馏进模型权重。

— Figure 7｜四类技能演化机制及其共同进入的技能库维护环节。
Critique-based 方法生成批评与修订，可用自评或外部工具、单元测试、沙箱通过率来把关；RL-based 方法把任务奖励拆给技能选择、使用和沉淀过程；Search-based 方法保留候选群体，用通过率、成本或多目标 fitness 选择；Distillation-based 方法把外部技能逐渐压入模型权重，减少运行时加载。四类方法的代价也不同：批评便宜但可能漂移，RL 自适应但样本重，搜索覆盖广但评估贵，蒸馏省加载却可能回归。

5.1接受一次修改之前，必须有证据闸门

纯自我批评容易让模型接受自己的错误，因此外部证据成为关键。CRITIC 使用工具结果，MUSE-Autoskill 附带单元测试，SkillOpt 只接受在留出集上提升的编辑，SkillCAT 还要让补丁通过任务克隆回放。论文的共同线索是：演化不是不断追加文本，而是 提出候选—验证收益—检查回归—再合入。

5.2技能库维护不是清理工作，而是长期正确性的组成部分

库变大后会积累近重复项、冲突修改、陈旧技能和拖慢检索的低价值条目。XSkill、SkillX 做合并；Trace2Skill 在合并时处理冲突，From Context to Skills 用旧案例回放检查；Skill-Pro、SkillMOO、SkillOS 依据贡献、搜索 fitness 或紧凑性奖励做裁剪。技能库若只有新增没有合并、版本与退役机制，规模越大并不意味着能力越强。

演化路线的差异最终必须通过评测来判断，但总任务成功率会把“技能本身好不好”和“Agent 是否会用技能”混在一起。论文因此在下一部分先把评测对象拆开。

— Figure 8｜Skill-centric 与 Agent-centric 两个评测目标。
图左固定 Agent，变化技能，测的是效果、复用、迁移、成本与安全；图右固定技能或技能池，变化 Agent，测的是选择、调用、应用、组合与鲁棒性。中间的天平表示两套分数不可互相替代：一个强模型可能掩盖差技能，一个好技能也可能被不会触发或不会落地的 Agent 浪费。

— Table 6｜四类演化方法与技能库维护的代表工作。
论文随后用 Table 6 收束演化方法的比较。Mechanism 列清楚标出 update target：self-critique、external check、policy + skill bank、genetic/frontier search、curriculum annealing、teacher–student，以及 consolidation、conflict control、pruning 与 health scoring。它为后续评测提供了可测对象：不同演化路线必须报告的不只是最终成功率，还应说明成本、迁移和回归。

06
EVALUATION
评测：拆开“技能好不好”和“Agent 会不会用”

有了双目标框架，评测才知道分数应该归因给谁。论文先列技能中心维度，再列 Agent 中心维度，最后用现有 benchmark 覆盖图暴露缺口。

6.1Skill-centric：固定 Agent，测技能的边际价值

— Table 7｜固定 Agent 时，技能质量应覆盖的八个维度。
八个维度从效果走向可部署性：相对 no-skill baseline 的任务成功增益；跨整个任务类别的复用；跨模型与跨环境迁移；每次加载和执行的 token 成本；规范质量；可组合性；以及是否不存在漏洞、注入指令和凭证泄漏。静态 rubric 可以低成本检查文件结构与风险，却不能证明技能有效；行为评测必须实际运行技能，并与关闭技能的对照组比较。

6.2Agent-centric：固定技能池，测智能体的使用能力

— Table 8｜固定技能池时，Agent 使用技能能力的八个维度。
这里的 Use 包括 selection、need-aware invocation、application 与 composition；Build 包括 creation 和 library maintenance；再加上面对干扰、冲突、过时或恶意技能时的 robustness，以及检索加载成本。一个 Agent 即使检索到了 gold skill，也可能不加载、错误调用或无法把步骤落到环境，因此 检索召回率只是链路中的一个信号。

6.3现有 benchmark 的空白在哪里

— Table 9｜Skill-centric benchmark 对八个维度的覆盖。
横向读取打勾位置可以看到明显空白：现有表格中 Cross-model、Cross-environment 与 Composability 三列没有专门 benchmark 覆盖；任务成功、规范质量和安全各自有部分工具，但同一 benchmark 很少同时覆盖效果、泛化、效率与安全。作者因此要求技能分数必须同时报告运行它的 Agent，否则不同论文之间无法比较。

— Table 10｜Agent-centric benchmark 对选择、调用、应用、组合、创建、维护、鲁棒性与成本的覆盖。
Agent-centric 一侧同样碎片化：SkillRouter、SkillRet 与 R3-Skill 聚焦选择；SRA-Bench 同时看选择与是否需要调用；SOP-Bench 看应用；SkillFlow、SkillLearnBench、SkillCraft、SkillGenBench、SkillEvolBench 分散覆盖创建、组合与维护；鲁棒性主要来自 SkillResolve-Bench、AgentTrap 和 When Safe Skills Collide 等安全研究。论文给出的最低报告标准是：技能论文至少报告成功增益、复用、执行成本和安全；技能型 Agent 至少报告选择、应用和鲁棒性。

评测维度一旦包含安全与鲁棒性，就不能把技能看成普通提示词。技能会携带文本、代码、元数据和长期权限，其风险更接近一条软件供应链。

07
SECURITY
安全与治理：技能也是软件供应链

技能比普通 Prompt 多三层风险：不受信任的文本进入模型上下文，打包代码在环境中执行，用户还可能对后续运行复用一次性批准。论文因此按威胁面、检测隔离与生态治理三层组织防线。

— Figure 9｜从威胁面到检测隔离，再到生态治理的安全框架。
左侧威胁包括正文注入、恶意代码、语义操纵、组合风险与技能窃取；右侧防线从静态检测升级到语义检测、行为验证和运行时权限隔离；底部治理则覆盖提交准入、持续质量控制、撤销披露以及跨平台来源信任。这个布局说明，单次扫描只能处理可见模式，长期可信需要发布前、运行中和生态层共同约束。

7.1攻击面不仅在代码，也在描述和组合关系

正文注入可以藏在 SKILL.md、引用脚本或人类不可见的 HTML 注释中；恶意 bundle 可带触发式后门；semantic compliance hijacking 不携带恶意代码，而是把越权目标包装成合规要求，让 Agent 自己生成并执行代码；描述文本还能操纵检索排名；两个单独安全的技能组合后也可能形成不安全链路。仅靠签名和 AST 扫描，无法覆盖这些语义与组合层风险。

7.2防线必须从检测延伸到最小权限和撤销

静态分析适合查找已知危险模式、secret 泄漏和代码结构；语义检测判断意图、权限理由与隐蔽行为；行为验证在沙箱中比较“声明做什么”和“实际做了什么”；permission gating 则用 contract、manifest 与 deny-by-default 限制一次调用的能力边界。进入 registry 后，还需要提交准入、证据门控更新、恶意条目撤销和 provenance。

— Table 11｜九类威胁、代表攻击、当前最佳防御与成熟度。
最后一列是论文对防御成熟度的判断。Bundled malicious code 与 credential leakage 被标为 Mature，因为已有静态或 AST 分析配合行为验证；body-level injection、compositional risk、persistent single-approval trust 与 skill stealing 仍是 Partial；无代码劫持、描述级供应链操纵和跨平台信任迁移 被标为 Open。最难的问题都藏在看似正常的文本和生态关系中，而不是显眼的 payload。

安全章节把论证推向最后一个问题：即使单个技能可用、可测、可扫描，技能库仍可能在长期增长、跨平台流转和自我演化中失去可靠性。

08
OPEN QUESTIONS
开放挑战：从单个技能走向可信生态

论文按“单个技能—技能库—生态系统”的尺度，列出六个尚未解决的问题。它们并不是新的算法清单，而是前面各章节暴露出的共性缺口。

•知道何时有用
技能收益会随任务、领域和 Agent 改变，作者和运行时都缺少可靠的 utility predictor。系统既要知道哪个技能相关，也要判断这次调用是否值得。

•外置还是内化
文本技能易审计、分享和修改，内化到权重后不占运行时上下文。尚缺少决定何种知识应留在工件、何时应迁入模型的机制。

•无回归演化
同一自我演化循环可能提升强模型、却拖累弱模型；单次验证闸门也无法保证长期任务流中的库整体单调改进。

•规模增长不衰减
技能库越大，选择质量可能下降，单个技能的错误还会扩散为全库漂移。版本、依赖、冲突和弃用需要像软件工程一样成为常规能力。

•跨框架可移植
结构化 IR 只能捕捉部分语义，而专门的跨模型、跨环境迁移 benchmark 仍缺位，导致可移植性既难实现也难测量。

•共享技能可信
来源、声誉与撤销状态尚不能随技能跨 registry 传播。一个在平台 A 下架的技能，仍可能在平台 B 以镜像或派生版本重新出现。

全文最后收束到一个一致结论：这个领域已经较擅长构建和使用 单个技能，却仍不擅长在规模下维护、评测和治理它们。Agent Skill 的研究重心因此会从“把诀窍装进文件”继续向库级运维、可归因评测、回归控制和跨平台信任移动。

✨ 一句话点评　Agent Skills 用“能力—过程—边界”的显式工件把任务诀窍从一次性上下文中解耦，也重新界定了 Agent 扩展能力的路径：可靠性不只来自更强的模型，还来自能被检索、验证、演化和治理的技能基础设施。
