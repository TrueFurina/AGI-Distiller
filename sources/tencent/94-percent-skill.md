## 核心痛点
1. 上下文塞不下：9000+源文件、跨5~6层调用，单轮对话喂不进去
2. 物料分散：PRD在TAPD、设计稿在Figma、协议在企微文档
3. 命名不一致：用户说"邮件点击入口"，代码里叫`didSelectRowAtIndexPath`
4. 模糊指令：用户一句"按PRD改一下"，AI跳过拆解直接改代码
5. 验证不闭环：AI报"完成"，结果编译都没过
6. 跨会话失忆：上一次的设计决策、改了哪些文件、为什么这么改，下一次全忘

## 核心解法

### 1. 8阶段流水线（Skill核心架构）
设计稿 → 拆解 → 定位 → 实现 → 验证 → 模拟器验证 → 沉淀 → 提交
每个阶段输入清晰、产出明确、退出标准可机器校验。

### 2. 五步定位法（从9000+文件找到改动点）
1. 意图消歧：项目概述~2K + 用户原话 → 4种技术解读
2. 模块定位：目录树 + 解读 → 2-3个候选文件路径
3. 关键词搜索：rg直接跑（不进LLM）→ 函数声明+位置
4. 调用链追踪：单个文件相关片段~10K → 完整调用链
5. 验证确认：函数实现~5K → 最终改动点+理由
关键：前2步只看目录和文件名，第3步才让脚本grep，到第4步才真正读代码

### 3. 三级金字塔知识库
- L1总览(overview.md)：模块名+一句话职责，<5KB，定位阶段默认preload
- L2模块(<module>.md)：每个.h/.mm文件+功能说明，命中模块后按需加载
- L3语义桥(figma_token_mapping.md)：Figma Token→工程API精确映射
自维护机制：SHA基线缓存+三色分诊清单+pre-commit hook阻断

### 4. 需求语义翻译
- 范围识别：硬关键词表（命中即强制打标签，不依赖LLM语义理解）
- 设计稿归宿：每张图必须归到三类之一，不允许"未归类"
- 拦截点清单：禁止语义联想，必须有具体引用依据
- 领域联想：5维搜索矩阵（iOS事件方法/功能语义/OC命名习惯/协议代理/通知回调）
- 翻译产物：五列表格+subtasks.json

### 5. 脚本优先于LLM
- 多源物料收集：每种来源一个专用脚本，严禁通用web_fetch
- 设计稿筛选：脚本直方图 vs LLM"手感"，严禁LLM手工分桶
- 落盘判定成功：sentinel文件=成功的唯一判据

### 6. 红线机制
- Critical（6条）：全流程必守，违反直接造成线上事故
- Standard（30+条）：按阶段加载，违反会污染工程规范
- 触发即停+模板化报告

### 7. 运行时验证
- 闸门一：编译验证（退出码0是唯一判据，自修复硬上限3轮）
- 闸门二：模拟器验证（真跑一遍+截图核对）

## 可执行规则
1. 知识库分三级：L1总览(<5KB) + L2模块(按需加载) + L3语义桥(精确映射)
2. 定位先看目录和文件名，再grep，最后才读代码
3. 任何"长跑命令"都不靠stdout报告成功，全靠落盘文件
4. 红线触发即停，按模板报告，不允许继续
5. 编译验证：退出码0是唯一判据，自修复上限3轮
6. 禁止LLM手工分桶，必须先用脚本处理数据
