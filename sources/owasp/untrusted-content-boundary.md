## 一、LLM01 提示词注入（来源 1，官方原文）

**定义**：当用户提示以非预期方式改变 LLM 的行为或输出时，即构成提示词注入。
官方特别指出：**这类输入即使人眼不可见也照样生效——只要被模型解析就行。**
（"prompt injections do not need to be human-visible/readable, as long as the content is parsed by the model"）

**RAG 与微调并不能消除该风险** —— 官方明确写了 research shows that they do not fully mitigate。

### 两类注入

| 类型 | 官方定义要点 |
|---|---|
| **直接注入** | 用户的提示输入**直接**改变模型行为；可以是有意的（攻击者构造），也可以是无意的（用户自己写出来的） |
| **间接注入** | LLM 接受**外部来源**（网站、文件等）的输入，外部内容里夹带的文本在被模型解析后改变其行为 |

> **间接注入是本文的重点**：只要 agent 读网页、读文件、读 issue/PR/评论，就在这个定义域内。

### 后果（官方清单）

泄露敏感信息 / 暴露系统提示与基础设施信息 / 内容被篡改导致错误或有偏输出 /
获得对 LLM 可用功能的未授权访问 / 在相连系统上执行任意命令 / 操纵关键决策过程。

### 七条缓解措施（官方原文编号）

1. **约束模型行为**：在系统提示里写清角色、能力与限制；强制遵守上下文；限制在特定任务/话题；
   指示模型忽略修改核心指令的尝试。
2. **定义并校验预期输出格式**：指定明确输出格式、要求给出推理与来源引用，
   并**用确定性代码**校验是否真的符合格式。
3. **实施输入与输出过滤**：定义敏感类别与处理规则；用语义过滤 + 字符串检查；
   用 RAG Triad（上下文相关性 / 扎根性 / 问答相关性）评估回答。
4. **强制权限控制与最小权限**：给应用自己的 API token；**在代码里而不是交给模型**去执行这些功能；
   限制模型访问权限到完成目标所必需的最小集合。
5. **高风险动作要求人工批准**：对特权操作实施 human-in-the-loop。
6. **隔离并标识外部内容**：把不可信内容**分离并明确标注**，以限制它对用户提示的影响。
7. **对抗性测试与攻击模拟**：定期渗透测试与入侵模拟，**把模型当作不可信用户**来测信任边界与访问控制。

### 九个攻击场景（官方原文，用于设计测试用例）

直接注入 / 间接注入（摘要网页触发图片外链导致对话外泄）/ 无意注入 /
有意的模型影响（改 RAG 语料）/ 代码注入（CVE-2024-5184）/ 载荷拆分（简历分两段拼出指令）/
多模态注入（图里藏指令）/ 对抗后缀（追加无意义字符串）/ 多语言或混淆（Base64、emoji 绕过过滤）。

## 二、LLM06 过度授权（来源 2，官方原文）

**定义**：开发者常给 LLM 系统授予一定"能动性"——调用函数或通过扩展（扩展/工具/skill/插件）
与其它系统交互。**过度授权**指：在 LLM 给出非预期、含糊或**被操纵**的输出时，
系统仍会执行破坏性动作——**不管 LLM 为什么失灵**。

官方列的常见触发：良性提示导致的幻觉 / 模型本身性能差 / **来自恶意用户的直接或间接注入** /
前一次被投毒或已被攻陷的扩展调用 / **多智能体系统中被攻陷的同伴 agent**。

**三个根因**（官方原文）：过度功能（excessive functionality）、过度权限（excessive permissions）、
过度自主（excessive autonomy）。

> 官方特别澄清：**过度授权 ≠ 不当输出处理（LLM05）**，后者关注的是对 LLM 输出的审视不足。

### 六类常见风险例（官方原文摘要）

1. 需要"读"文档，选用的第三方扩展却**同时带改和删**的能力。
2. 开发阶段试用过的扩展已被弃用，**却仍然挂着可用**。
3. 开放式的扩展**没把输入指令过滤到只允许那一个命令**（如"跑一条特定 shell 命令"实则能跑任意命令）。
4. 只需读数据的扩展，用**带 UPDATE/INSERT/DELETE 的身份**连数据库。
5. 面向单用户的扩展，却用**高权限通用身份**访问下游（一个用户能看到所有人的文件）。
6. 删除之类的高影响动作**没有任何用户确认**就执行。

### 八条缓解 + 两条减损（官方原文）

1. **最小化扩展**：只给完成目标必需的最小扩展集合（如不需要抓 URL 就别提供该扩展）。
2. **最小化扩展功能**：如摘要邮箱只需"读"，就不该含"删/发"。
3. **避免开放式扩展**：别用"跑 shell 命令 / 抓 URL"这类万能扩展，改用粒度化的专用扩展
   （要写文件就写一个只写文件的扩展）。
4. **最小化扩展权限**：连下游的身份权限压到最小（只需 `SELECT` 就别给写权限），并且**在下游系统上强制**。
5. **在用户上下文中执行扩展**：跟踪用户授权与安全范围，代表某用户执行的动作必须在**该用户上下文**中、
   以最小权限执行（如用 OAuth 的最小 scope）。
6. **要求用户批准**：高影响动作在**执行前**由人批准，可在下游系统或扩展内部实现。
7. **完全中介（complete mediation）**：**把授权放在下游系统，而不是让 LLM 自己判断该不该做**；
   所有经扩展发往下游的请求都要按安全策略校验。
8. **净化 LLM 输入与输出**：遵循 ASVS 等安全编码实践，重点在输入净化；在流水线里上 SAST/DAST/IAST。

**两条只减损、不防住的措施**：记录并监控扩展与下游活动；对动作做限速
（增加在造成重大损害前通过监控发现问题的机会）。

## 三、与本仓（AGI-Distiller）的实测对照 —— 2026-10-01

本仓的真实工作流与外部的交集（不是假设，是每天都在发生的事）：

| 本仓动作 | 对应风险 | 官方条款 |
|---|---|---|
| 蒸馏外部文章 / 抓网页 / 读第三方 README | **间接注入**（外部文本进上下文） | LLM01 |
| 读别人给的源码包、跑别人仓库的脚本 | 扩展/依赖被投毒；过度功能 | LLM01 + LLM06 例 1/3 |
| `bash` 一把梭（万能扩展） | **开放式扩展**（官方明确点名 "run a shell command"） | LLM06 缓解 3 |
| 提交/推送/删除等不可逆动作 | 过度自主（缺执行前人工批准） | LLM06 例 6 + 缓解 6 |

**对照结论**：本仓 `AGENTS.md` 的绝对红线已经天然覆盖了一部分（红线 3「不操作生产服务」、
红线 4「不提交或推送，等用户确认」= 缓解 6 的"执行前人工批准"）。
缺的是**输入侧**那一半：**没有一条纪律说"外部内容一律当数据不当指令"**。这正是新 skill 要补的。
