# Long Task Resume — 断点续跑纪律

## 设计四要素（写长任务脚本前先定）
1. **检查点先行**：进度落盘（`checkpoint.json`：已完成的 key 列表 / 最后游标），每处理 N 条更新一次——中断后从检查点续，不从头再来。
2. **幂等可重跑**：同一输入跑两遍结果一致——按 key 去重跳过已完成项；写文件用"临时文件 + 原子 rename"，不直接覆写。
3. **sentinel 判成功**：结尾写 sentinel 文件（`DONE` 含统计摘要）——**成败看落盘，不看 stdout**；过滤管道（`| grep -v`）会吞失败行得出假全绿。
4. **恢复命令显式化**：脚本支持 `--resume` 从检查点续跑；把恢复命令写进日志尾部，中断后一条命令接着跑。

## 中断后恢复 SOP
1. **看检查点**：`checkpoint.json` 确认断在哪（最后成功的 key/游标）
2. **清点产物**：已生成的文件是否完整（对照预期清单）；半截文件按幂等设计重做
3. **`--resume` 续跑**：不改动任何已完成产物
4. **对账**：跑完后 sentinel/统计 与预期总数核对（预期 100 → 实际 99 = 有 1 条静默失败，逐条查）

## 真实教训映射（为何每条都是铁律）
- bash 300s 超时中断批量调用 → 靠"已成功的跳过"断点续跑补完剩余 10 个（检查点+幂等）
- 双盘符路径（`E:/e/Program/...`）致 pytest 全 ERROR → 环境变量/路径参数先验再跑，别跑完 40 个包才发现
- 深度思考中断 → plans/current.md 记"已完成/进行中"即人肉检查点

## 前置防御
- 超长批量任务预估耗时 > bash 上限（300s）→ 必须设计为可分批/可续跑，或后台化 [实测]
- 网络型跑批（API 调用）→ 内置退避重试 + 失败清单落盘（哪些 key 失败、原因），续跑只补失败项
- 成本型跑批（付费 API）→ 先跑 ≤5 条小子集验证全链路，再放量（烧钱事故纪律）
