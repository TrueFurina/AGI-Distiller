# 任务说明模板

用户请求: $ARGUMENTS

## 规则

1. **收到一句话任务，先追问缺失要素，不直接开写。** 需求越模糊，返工成本越高。
2. 6 要素中缺哪项问哪项，已给出的不重复问。
3. 追问用选择题/填空形式，不用开放式"你想要什么"。
4. 用户补齐后，先复述确认再动手。

---

## 6 要素结构

### 1. 背景
- 当前功能/页面/接口的用途是：
- 现在遇到的问题是：
- 影响的用户或业务场景是：

### 2. 目标
- 本次要实现：
- 本次不做：

### 3. 范围
- 优先查看这些文件或目录：
- 可能相关的旧逻辑：
- 需要保持兼容的行为：

### 4. 限制
- 不要改：
- 不要新增：
- 如需扩大范围，先说明原因再动手

### 5. 验收标准
- 用户看到的结果：
- 需要覆盖的边界场景：
- 需要运行的检查命令：

### 6. 交付
- 先简述方案
- 修改后列出：改了哪些文件、怎么验证、还有哪些风险

---

## 执行步骤

### 步骤 1：判断任务完整度

检查用户输入是否覆盖 6 要素。一句话任务（如"帮我做个用户管理"）通常只给了目标的一半。

### 步骤 2：追问缺失项

只问缺失的，用具体选项降低用户回答成本：

```
背景缺 → "这个功能现在给谁用？解决什么问题？"
目标缺 → "本次要做到什么程度算完成？有哪些明确不做？"
范围缺 → "先看哪个目录？有没有要兼容的旧逻辑？"
限制缺 → "哪些文件/模块绝对不能动？"
验收缺 → "用什么现象/命令判断做对了？"
交付缺 → "要我直接改，还是先给方案？"
```

### 步骤 3：复述确认

用户补齐后，用自己的话复述一遍 6 要素，确认无误再开始。

### 步骤 4：输出结构化任务说明

按上方 6 要素格式输出完整任务说明，作为后续执行的唯一依据。

---

## 输出格式

```

### 目标
- 实现：...
- 不做：...

### 范围

...

### 交付
...
```
