# 自动化任务灰度发布

## 设计四要素（缺一不建）
1. **频率**：明确到时刻（"每周五 17:00"、"工作日 9:00"）——不写"定期""偶尔"
2. **动作**：步骤编号的确定性指令（读什么、怎么加工、判断口径写清）——不写开放式描述
3. **产出**：固定落盘路径 + 文件名规则（`weekly-YYYY-MM-DD.md`）——**落盘文件是唯一成功判据**，stdout 报告不算数
4. **例外**：显式写入（"周末跳过"、"7 天无更新输出一行报告"）——不写"一般情况"

## 灰度纪律（官方建议，强制执行）
1. **先手动触发 1 次**：确认任务对指令的理解、路径读取（尤其中文路径）、产物落盘全部正常
2. **验证产物**：文件存在 + 内容正确 + 字数约束满足——不信任务自述，只看落盘
3. **再挂定时**：挂上后首周抽查 1-2 次执行记录，确认无静默失败
4. **放大频率**：先低频（每周）跑稳，再考虑加密（每日）——反向不成立

## 成本控制
- 简单检查/汇总任务用快速或均衡档，不用深度推理档
- 字数上限、条数上限写进 prompt（"报告不超过 500 字"）——减少返工轮次，自动化同样"每多一轮多一份消耗"
- 信息源分级：只读本地的汇总类消耗低；含联网搜索的早报类消耗中——按需选择
- 每周抽查执行记录：网络/登录异常会导致**静默失败**（无产出且无报错）

## 质量红线（来自真实试运行）
- 只读类任务：**不修改任何源文件**，只新建汇总/报告文件
- 判定口径写进 prompt 并让任务自述口径（如"系统理解任务不计入积压"）——没有口径的任务会为凑结果而扩大范围
- 空数据路径：无更新时输出一行"无新增"，不生成空文件
